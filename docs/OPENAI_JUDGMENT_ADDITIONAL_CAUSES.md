# 하루단어 AI 참고 의견 추가 원인 조사 · 2026-11-03

**추가 조사 완료, 제품 수정·재평가·배포 없음.** 앞서 확인한 목표/문법 라벨 혼동·문맥 보류·의도 보존 문제 외에, 과거 의견 재사용과 응답 검증 경로의 결함을 재현했다. 입력 전달 범위와 진단 정보에도 한계가 있다. 이를 모두 모델의 문법 생성 오류로 묶어 설명하면 안 된다.

이 조사는 게시 확인된 v142의 동결 소스 `8f312b3a4217d0118d3971578a05dd63db7f5624`와 비활성 후보 `f273886f43324d4a668ecc6550a97bb8ebcfda56`를 대상으로 한다. 운영 계정·개인 학습 기록은 읽지 않았다. 특정 사용자가 본 오류의 직접 원인까지 확정한 조사는 아니다.

## 1. 모델을 바꿔도 같은 문장의 과거 의견에 머물 수 있다

운영 `sentenceFeedbackPresentation`은 저장된 의견의 `original`과 현재 문장이 같으면 요청 버튼을 잠근다. 현재 선택 모델·저장 의견의 제공사·프롬프트 버전·목표 뜻의 동일성은 확인하지 않는다. 화면은 저장된 `aiFeedback`을 그대로 보여 준다.

- 과거 Gemini 합성 의견도 저장 스키마를 통과하고, 같은 문장에서 `reviewed / disabled=true`가 됐다. 서버 렌더링에도 과거 Google 제공사 표시가 남았다.
- 다른 OpenAI 모델의 저장 의견으로도 같은 잠금이 재현됐다. 모델 설정 변경이 과거 의견을 새 모델로 재생성한 결과라는 뜻은 아니다.
- 문장을 바꾸면 ‘수정 전 문장’이라는 안내는 나오지만, 과거 교정문을 적용하는 버튼은 계속 허용된다. 클릭하면 그 교정문 전체로 바꾼다. 이는 새 모델이 낸 오류와 구분해야 할 재사용 경로다.
- 후보는 같은 문장도 명시적으로 재요청할 수 있도록 구현돼 있다. 그러나 후보 전체가 미배포이므로 운영의 이 잠금은 그대로다.

## 2. 운영 검증기는 ‘문법 보완 필요’인데 교정이 없는 응답도 허용한다

운영 파서는 `natural`이면 원문 그대로, `uncertain`이면 빈 교정문을 요구한다. 그러나 `needs_work`에는 실제로 다른 교정문이 있어야 한다는 조건이 없다.

합성 원문 `She go to school.`에 `grammar=needs_work`를 붙이고 교정문을 비우거나 원문 그대로 두어도 파서를 통과했다. 모델이 오류를 지적하면서 고치지 못한 응답이 형식상 정상으로 전달될 수 있다.

후보 파서는 문맥 보류가 아닌 `needs_work`에서 이 두 응답을 거절한다. 이 부분은 후보에 보완돼 있지만 운영에는 반영되지 않았다.

근거: [운영 판정 검증](../work/openai-api-migration-20261103/lib/provider-feedback-contract.ts), [후보 판정 검증](../work/judgment-improvements-20261103/lib/judgment-feedback-contract.ts).

**확정 범위:** 합성 응답의 허용/거절. 이번 OpenAI 정상 생성 294건에서 이 형태가 실제 반환된 횟수는 0이다. 사용자 오류의 발생 빈도를 입증하는 결과가 아니다.

## 3. 교정문이 맞아도 잘못된 문법 설명이 그대로 표시될 수 있다

교정문·라벨·설명이 서로 맞는지, 설명에 쓴 문법 규칙이 참인지 일반적으로 확인하는 장치는 없다. 운영의 추가 안전 검사는 구조 분석의 특정 진행형·arrive 전치사구 모순에 한정된다. 후보의 가시 설명 검사도 해당 유형 중심이다.

`She goes to school.`을 그대로 반환하면서 ‘goes는 go의 과거형’이라는 잘못된 합성 설명을 붙였을 때, 운영과 후보 모두 파서·안전 검사를 통과했다. 두 버전의 실제 `FeedbackDetail` 서버 렌더링에도 잘못된 설명이 남았다.

근거: [운영 안전 검사](../work/openai-api-migration-20261103/lib/feedback-safety.ts), [후보 가시 설명 검사](../work/judgment-improvements-20261103/lib/learning/feedback-safety.ts), [설명 표시](../work/openai-api-migration-20261103/app/feedback-detail.tsx).

## 4. 화면에서 숨긴 구조 분석의 실패가 올바른 교정문까지 막는다

운영 API는 구조 분석을 화면에 표시하지 않아도 생성 응답에 필수로 요구하고, 전체 응답을 한꺼번에 검증한다. 구조를 제외하는 구형 호환 변환도 이 검증 뒤에 실행된다.

실제 운영 어댑터에 모의 HTTP200 응답 두 개를 넣었다. 둘 다 `She go to school.`을 `She goes to school.`로 정확히 교정했다. 구조 분석에서 마지막 마침표 하나만 빠뜨리자 전체 결과가 `provider_invalid_response / structure`로 거절됐다. 교정 부분의 정오와 응답 전체의 수용 여부가 결합돼 있다.

생성용 JSON 스키마와 로컬 제한도 완전히 일치하지 않는다. 예를 들어 생성 스키마는 설명을 단순 문자열로 정의하지만 로컬은 1,500자로 제한한다. 스키마 형식에는 맞는 합성 1,501자 설명은 로컬 `fields` 단계에서 전체 거절됐다.

**확정 범위:** 정확한 교정문이 다른 필드의 오류로 사라지는 실패 경로를 재현했다. 이번 OpenAI 원장에서 확인된 실패 4건의 단계는 모두 `judgment`이며, 위 구조·길이 실패가 실제 4건의 원인이라는 뜻은 아니다. 후보의 새 판단 경로는 숨긴 구조 생성을 제거했다.

## 5. 화면에 있는 정보가 전부 AI 문맥으로 전달되지는 않는다

실제 전송 함수를 오프라인으로 실행해 요청 본문을 포착했다. 오늘의 단어 학습은 `word / pos / meaning / sentence`만 보낸다.

- 화면 ‘보완할 점’의 ‘전치사 확인하기, 과거형으로 바꾸기’ 같은 메모는 전송되지 않는다. 현재 API 요청 스키마도 `notes` 필드를 거절한다.
- 이전 문장·일반 ChatGPT 대화·추가 의도 설명도 전달하지 않는다. 매번 단일 user 입력이며 conversation/previous_response_id가 없다.
- 문법 수업 요청에는 target/role/pattern/task/check가 있지만, 과제가 가리키는 원래 문장 틀인 `stem`은 없다. 예를 들어 명사 과제의 ‘music을 … 바꾸기’는 전송되지만 `I like music.`이라는 문장 틀 자체는 별도 필드로 보내지 않는다. pattern의 예문이 일부 단서를 줄 수는 있다.

근거: [요청 훅](../work/openai-api-migration-20261103/app/study/use-sentence-feedback.ts), [단어 API 입력 조립](../work/openai-api-migration-20261103/app/api/sentence-feedback/route.ts), [문법 입력 조립](../work/openai-api-migration-20261103/lib/grammar/feedback.ts), [메모 UI](../work/openai-api-migration-20261103/app/study/sentence-stage.tsx).

**확정 범위:** 전송되는 정보의 범위다. 메모를 AI로 보내겠다는 현재 UI 약속은 없으므로 단순 누락 버그로 단정하지 않는다. 부족한 문맥이 각 오판에 얼마나 영향을 줬는지는 미입증이다. 개인 메모를 무조건 AI에 추가 전송하자는 결론도 아니다.

## 6. 프롬프트의 목표 보존 지시와 검증 조건 사이에 긴장이 있다

운영 지시는 ‘의도와 오늘 목표 용법을 보존하는 교정’을 요구하는 동시에 ‘맞는 문장은 그대로 반복’하라고 한다. 목표 뜻·품사가 틀렸지만 문법은 자연스러운 경우 무엇을 우선할지 충분히 명확하지 않다. 검증기는 `natural`을 반환하면 교정문을 원문과 한 글자도 바꾸지 못하게 한다.

기존 원장에서 `book=예약하다(동사)`를 목표로 한 `This book is interesting.`은 세 모델 모두 응답 후 `judgment` 검증에서 거절됐다. `bank=은행` 목표의 `I sat on the river bank.`도 기준선 Terra에서 같은 단계로 거절됐다. 이 4건은 키·결제·네트워크 실패나 출력 한도 초과로 분류된 건이 아니다.

다만 거절된 응답 본문은 보관하지 않았다. `natural`인데 교정문을 바꿨는지/비웠는지, `uncertain`인데 교정문을 남겼는지까지 복원할 수 없다. 따라서 위 지시의 긴장을 **설계상 위험**으로 확인했지만, 특정 문구 하나가 4건을 발생시켰다고 확정하지 않는다.

원문을 보관하지 않고도 향후 `natural_changed_correction`, `natural_empty_correction`, `uncertain_nonempty_correction` 같은 고정 사유를 구분하면 이 관측 공백을 줄일 수 있다. 이번에는 구현하거나 새 응답을 수집하지 않았다.

## 저장된 실패의 재분류와 배제한 설명

원점수·개별 검토·고정 분모·출시 판정을 바꾸지 않고, 이미 수집된 결과만 사후 분해했다.

| 관측 | 결과 | 의미 |
|---|---:|---|
| 정상 생성·채점 조합 | 294 | 기준선 205, 후보 89; 전체 계획을 측정한 것은 아님 |
| 고정 5차원/핵심 오류 기준 실패 | 25 | 미측정·형식 실패와 별도 |
| 목표 라벨만 불일치 | **21** | 기준선 11, 후보 10; 다른 4차원은 통과 |
| 나머지 문맥 보류·해석 실패 | **4** | 후보의 Music 1, Exactly six… 2, eat go 1; 그중 확인된 의도 창작 1 |
| 정상 생성의 요청/실제 모델 일치 | 294/294 | 이 자료에서 몰래 다른 모델로 대체된 증거 없음 |
| 기준선/후보 정상 출력 최대 토큰 | 434 / 261 | 설정 상한 4,096 미만; 정상 결과의 일반 품질 문제를 잘림으로 설명할 근거 없음 |
| 실패 생성의 기록된 단계 | judgment 4 | 연결 실패와 앱의 판정 거절을 구분해야 함 |

21건은 일반 ChatGPT에서 문법을 고칠 수 있는지와 다른 실패 기준이다. 나머지 4건도 모두 서로 다른 영어 문장 4개라는 뜻은 아니며 같은 문장·다른 모델 조합을 별도로 센 것이다. 새 평가 점수나 일반 사용 정확도로 환산하지 않는다.

모델별 `reasoning.effort`는 실제 전송에서 `low`로 고정돼 있다. 정상 생성 중 reported reasoning token=0은 기준선160/후보59건, 양수는45/30건이다. 0이라는 메타데이터를 ‘생각을 전혀 하지 않았다’고 해석하지 않는다. 더 높은 설정이나 일반 ChatGPT와 같은 조건의 비교는 하지 않아, low 설정의 인과 효과는 미확정이다.

## 우선순위와 이번 변경 범위

1. 과거 의견의 출처·입력·목표·모델과 새 요청을 구분하고 명시적 재점검을 허용한다. 현재 후보에 구현한 기능과 운영 상태를 분리해 판단한다.
2. 문법 보완 필요/교정문/설명의 일관성, 목표 뜻 불일치 시 원문 보존을 하나의 명확한 계약으로 맞춘다.
3. 불필요한 부가 분석 때문에 올바른 교정까지 사라지는 결합과 생성/로컬 스키마 차이를 줄인다. 정확도 검증을 약하게 만들어 통과율을 올리는 방식은 피한다.
4. 필요한 의도·추가 문맥을 명시적으로 받을지 설계하고, 전송 범위와 개인정보 안내를 함께 맞춘다.
5. 실패 사유는 고정 코드로 더 구체화한다. 개인 문장·응답 원문을 진단 로그에 추가하지 않는다.

위는 조사 결과에 따른 후속 우선순위다. 이번 요청은 조사이므로 제품 코드·프롬프트·운영 설정·DB·개인 기록을 수정하지 않았다. 후보는 계속 비활성·미게시이며 기존 품질 게이트 실패·US$5 상한·추가 평가 예약 불가 판정을 유지한다.

## 검증과 재현

```powershell
# 키를 읽지 않으며, global fetch는 차단하고 제공자 HTTP 응답은 로컬에서만 모의한다.
node .taskmaster/scripts/investigate-additional-judgment-causes.mjs
```

실제 두 소스의 함수·React 표시 컴포넌트를 묶어 실행하는 32개 검사, 모의 제공자 처리 4회, 실제 제공자 요청 0회다. 결과는 `outputs/openai-migration-release/additional-investigation/results.json`, 실행 출력은 같은 상위 폴더의 `additional-investigation-run.log`에 남긴다. 원래 원장/개별 검토/평가 기준과 루트 제품 파일 13개의 바이트 해시, 두 동결 체크아웃의 HEAD·clean 상태를 전후 대조한다. 결과에 새 개인 문장·제공자 응답 본문을 복사하지 않는다.
