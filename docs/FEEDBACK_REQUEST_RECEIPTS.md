# AI 요청 영수증 — Task14.2, 미게시 후보

문장 점검은 새 사용자 버튼에서만 시작한다. 계정+UUID를 제공자 호출 전에 D1에 원자 기록하고 같은 ID는 7일 유효 범위에서 다시 실행하지 않는다. 응답 유실 후 첫 버튼은 이전 결과를 GET으로 확인하며 같은 클릭에서 새 요청으로 대체하지 않는다. 실패·불명·만료를 확인한 뒤 다음 버튼은 새 유료 요청임을 알린다. 자동 재시도·폴링·모델 대체·일일 호출 제한·결제 변경은 없다.

## 개인정보와 보관

- `feedback_requests`: 소유 계정, 요청 UUID, 문장/목표/실제 프롬프트/모델/반환 계약의 SHA-256, 도메인/대상 ID, 상태와 시각, 안전한 앱 응답을 저장한다. 키·원시 제공자 응답/오류는 저장하지 않는다.
- 앱 응답(원문·교정·설명)은 24시간 복구할 수 있다. 최소 ID/지문/상태는 요청 시작부터 7일 유효하다. 소유 계정의 다음 POST/GET에서 만료 본문/행을 정리하므로 닫힌 사이트에서 물리 삭제 시각을 보장하지 않는다.
- 기기의 입력·요청 UUID는 별도로 최대7일/20행/1MiB/단일64KiB 안에 평문 보관한다. 설정의 기기 삭제·앱 로그아웃은 로컬 자료만 제거한다. 서버 학습 기록/영수증 보관과 구분한다.
- 전체/분할 복원이나 대상 학습 삭제는 SQL trigger로 해당 응답을 원자적으로 무효화한다. 중복 방지용 tombstone은 유지한다. 계정 프로필 삭제는 FK cascade다. 학습 백업/revision에 영수증을 섞지 않는다.
- 클라이언트에서 복원 완료를 확인하거나 복원 시도 뒤 서버 기록을 다시 불러오면 이 브라우저의 임시 초안/이전 요청 정보를 정리한다. 이전 기기 제안이 복원한 백업을 다시 덮어쓰지 않게 한다. 복원 확인 창에서 이를 안내하고 먼저 현재 입력을 백업한다. 알림은 시작 당시 계정의 등록 세대를 확인하므로 다른 계정으로 전환한 뒤 늦은 복원 응답이 새 계정 캐시를 지우지 않는다.

## API와 실패 처리

성공 HTTP 응답이라도 완료 영수증이 없거나 형식이 잘못됐으면 클라이언트는 `invalid_response`로 표시하고 pending UUID를 보존한다. 다음 사용자 클릭은 같은 UUID의 GET 조회만 수행한다. 형식 오류를 처리 불명 오류로 바꾸거나 같은 클릭에서 새 POST로 대체하지 않는다.

두 기존 POST는 optional `requestId` UUID/`requestStartedAt` 정수 쌍을 받는다. 새 클라이언트는 항상 쌍을 보내고 제공자 호출 전 기기 보관까지 확인한다. 과거 v142 클라이언트의 필드 없는 요청은 기존 계약을 유지하므로 그 클라이언트에는 새 멱등성을 소급 보장하지 않는다.

```json
{"requestId":"a1111111-1111-4111-8111-111111111111","requestStartedAt":1793664000000}
```

예시의 시각은 설명용이다. 기기 시각이 서버보다 60초 이상 미래이면400, 7일 이상 오래된 요청은410이며 제공자를 호출하지 않는다. 같은 ID의 다른 목표/문장/모델/프롬프트/반환 계약은409다. claim에는 문맥을 읽은 학습 revision도 비교해 그 사이 저장/복원이 일어났으면 호출 전에 거절한다. revision은 지문에 고정하지 않아 동일 내용의 단순 저장 뒤에도 기존 결과를 확인할 수 있다.

`GET /api/feedback-requests/:id`는 로그인한 소유자만 조회하며 AI master switch가 꺼져 있어도 제공자 없이 작동한다. 완료200/처리 중202/실패의 기존 HTTP 상태/불명409/만료410/다른 계정404를 구분한다. 2분 이상 응답 없는 pending은 불명으로 표시하며 실행권을 가져오지 않는다. 늦은 정상 완료는 복원으로 무효화되지 않은 pending에만 저장한다.

claim/정리 DB 오류는503과 제공자0회다. 완료 본문 저장 실패는 받은 결과와 `receipt.persisted:false`를 반환하고 이미 쓴 claim을 유지한다. 클라이언트는 결과를 기기에 보관하고 서버 학습 기록에 저장을 시도하되 동일 ID를 재실행하지 않는다. 운영 통계 쓰기 실패는 앱 소유의 안전한 코드만 기록하고 생성을 막지 않는다.

## 마이그레이션·배포·롤백

1. 생성한 `drizzle/0006_feedback_request_receipts.sql`·`meta/0006_snapshot.json`·journal과 schema를 함께 검토한다. 기존0000~0005는 수정하지 않는다. 새 테이블/인덱스와 대상 DELETE trigger만 추가하며 backfill은 없다.
2. 루프백의 별도 D1에 기존 migration과0006을 적용하고 소유권·동시 claim·각 실패·만료·전체/분할 복원 원자성을 검사한다. 로컬 적용은 운영 적용이 아니다.
3. Task15의 운영 gate 뒤 기존 Site에 같은 소스를 게시한다. Sites는 migration을 Worker 앞에 적용한다. 판단 v2는 품질 G4가 통과할 때만 `feedback_judgment_enabled=true`로 켠다. 미실측이면 false를 유지한다.
4. 문제가 있으면 AI master switch를 끄고 입력/백업 reader 및 새 영수증 POST/GET reader를 유지하는 버전으로 되돌린다. 구형 v142만 그대로 게시하면 열린 새 클라이언트의 필드와 GET을 지원하지 않으므로 호환 롤백이 아니다. judgment flag off는 기존 v1 생성/파서를 사용하면서 새 영수증 계약을 유지한다.
5. 적용한0006과 table을 삭제하지 않는다. 실패한 게시에도 migration은 적용됐을 수 있으므로 원격 적용 상태부터 확인한다. 파괴적 down migration이나 기존 학습 기록 재작성은 하지 않는다.
