## 초기 구동과 이미지 요청

기준 main 빌드와 최종 빌드에 각각 새 루프백 Worker·가상 D1을 사용했다. 동일한 0/365/1,825회차 자료, Chromium 390×844, CPU 4배 지연, 새 브라우저 컨텍스트/캐시 없음, 이미 준비된 Worker에서 조건별 3회씩 교대 측정했다. 느린망은 지연 150ms·다운로드 500,000B/s·업로드 125,000B/s다.

## 실패 이력과 확인 한계

- Windows에서 실행 중인 미리보기가 `dist/client`를 잡고 있어 재빌드가 `EBUSY`로 종료 1이었다. 소유 서버를 종료한 뒤 재빌드했고, 이후 QA는 복사한 고정 빌드로 실행했다. 최종 빌드/QA 복사본 지문을 대조한다.
- 첫 종합 검사에서 ‘발음’과 ‘음성 도움말’ 두 summary가 잡혔다. 정확한 ‘발음’ 선택자로 고친 뒤 검사했다. 기대 동작을 완화하지 않았다.
- 로컬 Wrangler에서 **본문이 있는 PUT을 401로 거부한 뒤 연결을 재사용하면 다음 조회가 지연**되는 현상을 짧은 검사로 재현했다. 변경 전 main의 기존 `/api/state`도 `GET 200 → PUT 401 → 다음 GET timeout`이었다. 본문 취소만으로 해결되지 않아 그 변경은 제거했다. 중간에 Wrangler 종료도 관찰했으며 하위 구현 원인/운영 재현 여부는 미확정이다. 최종 브라우저 검사는 신규 계정 독립 위치를 먼저 확인하고 이전 계정 화면의 401/쓰기 중단으로 마친다. 이 로컬 연결 재사용 문제를 해결했다고 주장하지 않는다.
- 기존 SQL과 Git blob의 첫 원문 SHA 대조는 Windows CRLF/LF 차이로 실패했다. 파일을 수정하지 않고 Git의 실제 clean filter를 적용한 blob과 기존 schema 객체를 대조해 보존을 확인했다. 기본 폴더 파일은 원래 디스크 SHA 그대로 비교했다.
- 실제 iPhone Safari/홈 화면·VoiceOver, 운영 계정/운영 DB, 운영 AI·결제, 실기기 저장/재접속은 미검증이다. GitHub 원격 CI는 푸시 후 PR의 체크 기록으로 별도 확인하며 위 로컬 검사의 성공과 구분한다.

## 변경 경계와 운영 준비

기본 폴더의 기존 변경은 계획 작성 때의 18개에 계획/프롬프트 2개가 더해져 작업 시작 시 **20개**였다. 상태·경로·디스크 SHA를 전후 비교해 그대로 보존했다. 지정 이미지 worktree만 수정했으며 기본 폴더 브랜치를 전환하지 않았다.

기존 SQL/snapshot 10파일과 기존 journal 5항목을 유지했다. `db:generate`가 추가한 테이블 하나와 새 snapshot/journal 항목만 사용한다. `.openai/hosting.json`, 바인딩, 의존성/lockfile, 기존 학습 API·저장소·백업 소스는 Git 기준과 동일하다. 임시 DB마다 미적용 마이그레이션만 한 번씩 실행했으며 운영 DB에는 적용하지 않았다.

위험도는 중간이다. 위치는 학습 revision·성적·일정·백업과 분리된다. 위치용 계정 ID·카드 이동 이력을 진단에 추가하지 않는다. 향후 게시 때 기존 Sites 절차로 새 테이블 적용을 확인해야 한다. 롤백은 이전 앱으로 돌아가되 위치 테이블/데이터를 남기며 학습 기록을 복원하거나 DROP하지 않는다. 실제 운영 게시/롤백은 미실시다.
